최적화 알고리즘으로 대학원 논문을 쓰려다 보니, 지금 있는 의료 쪽 말고 다른 도메인도 해보고 싶어졌다.  
대학원에서 그냥 쓰던 도구를 조금 더 업그레이드하는 것보다는, 더 많은 도메인을 접할 수 있으면 좋겠다는 생각이 들어서다.  

마침 나는 벤더 출신이라 제조 플로우를 어느 정도 안다.  
생산 내부의 관리를 자동화하는 MES에 OR을 붙여볼 수 있겠다는 생각이 들어서 공부를 시작했다.  

**이 글은 그 첫 정리다. MES가 무엇이고, 왜 내가 하던 근무표 문제와 구조가 닮았는지까지 적는다.**  
측정이나 실험은 없다. 개념을 잡는 단계의 기록이고, 재는 것은 스키마를 설계한 뒤의 일이다.  

## MES가 뭔가

### 계획만으로는 제품이 안 나온다

회사가 오늘 이런 결정을 했다고 하자.  

> A제품 10,000개를 금요일까지 생산한다.  

이건 주로 ERP나 생산계획 시스템의 영역이다.  
그런데 실제 공장에서는 바로 질문이 쏟아진다.  

* 지금 몇 개 만들었지?  
* 어느 공정까지 갔지? 어떤 설비에서 만들고 있지?  
* 설비 하나가 고장 났는데 어느 제품이 영향받지?  
* 불량이 발생한 제품은 어느 LOT이지? 어떤 원료와 Recipe로 만들었지?  

이걸 실시간으로 관리하는 시스템이 MES(Manufacturing Execution System, 생산실행시스템)다.  

![ERP와 MES, SCADA/PLC 3계층과 각 층이 답하는 질문. 위에서 생산지시가 내려오고 아래에서 실적과 설비상태가 올라간다](/assets/images/2026-08-14-mes-basics/01-layers.png)

자료를 보다 보니 ISA-95라는 말이 계속 나왔다.  
찾아보니 제조 시스템의 계층을 정의한 국제표준(IEC 62264)이었고, 위 그림처럼 Level 0부터 4까지 번호를 매겨 나눈다.  
ERP가 Level 4, MES가 Level 3, SCADA/PLC가 Level 0~2다.  

이 표준이 왜 중요한지는 나중에 알았다.  
"MES가 어디까지 책임지는가"를 말로 다투지 않고 **번호로 가리킬 수 있게** 해주는 공통 언어라서다.  
현업에서 "그건 L3 영역이죠"라고 하면 그 한마디로 경계가 정리된다.  

백엔드 개발자 기준으로 보면 MES는 공장의 핵심 업무 백엔드에 가깝다.  

### ERP와 MES의 경계

공부하면서 가장 중요하다고 느낀 게 이 경계다.  
두 시스템이 답하는 질문이 다르다.  

| | 답하는 질문 | 다루는 것 |
|---|---|---|
| ERP | 무엇을 얼마나 언제까지 만들 것인가 | Product, CustomerOrder, ProductionOrder, BOM, 납기 |
| MES | 지금 그것이 어디서 어떤 상태로 만들어지고 있는가 | Lot, Route, Operation, Equipment, WIP, Dispatch, Trace |

표에 있는 BOM(Bill of Materials)도 처음 보는 말이었다.  
찾아보니 자재명세서, 그러니까 "이 제품 하나를 만들려면 무슨 부품이 몇 개 필요한가"를 적어둔 목록이다.  
소프트웨어로 치면 의존성 목록(`package.json`)에 가깝다고 생각하니 바로 이해가 됐다.  

경계를 규칙으로 적으면 이렇게 된다.  

* ERP는 LOT을 모른다. 생산지시(PO) 단위로만 이야기한다  
* MES는 원가와 고객을 모른다. PO의 수량과 납기, 우선순위만 받는다  
* PO 1,000개를 LOT 20개로 쪼개는 결정은 MES의 권한이다  
* 생산실적은 MES → ERP 단방향이다. ERP가 MES 상태를 직접 바꾸지 않는다  

이 선이 흐려지면 "누가 무엇의 주인인가"가 사라진다.

### 핵심 엔티티

몇 개만 알면 절반은 이해한 셈이다.  

| 엔티티 | 뜻 |
|---|---|
| Production Order | 무엇을 얼마나 만들라는 생산지시 |
| Lot | 생산을 추적하는 단위. 모든 추적성의 주어 |
| Route | 제품이 거쳐야 하는 공정 순서 |
| Operation | 개별 공정 (예: CUTTING, INSPECTION) |
| Equipment | 실제 작업하는 설비 |
| WIP | Work In Process. 아직 생산 중인 재공품 |
| Recipe | 특정 제품을 설비에서 어떻게 처리할지 정한 조건 |
| Dispatch | 어떤 LOT을 어떤 설비에 넣을지 결정 |
| Hold / Release | 문제가 있는 LOT을 멈추거나 다시 진행 |
| Traceability | 어떤 제품이 언제 어느 설비와 공정을 거쳤는지 이력 |

표를 만들면서 특히 헷갈렸던 세 개는 따로 찾아봤다.  

**WIP**는 Work In Process의 약자로 재공품이라고 번역한다.  
착수는 했는데 아직 안 끝난 물량, 즉 공장 안에 떠 있는 재고를 말한다.  
찾아보니 제조에서 WIP가 많다는 건 대체로 나쁜 신호였다. 돈이 창고가 아니라 라인 중간에 묶여 있다는 뜻이라서다.  

**Recipe**는 요리법이라는 말 그대로다.  
같은 설비라도 제품마다 온도와 시간, 압력 조건이 다른데, 그 조건 묶음을 Recipe라고 부른다.  
그래서 "이 설비는 이 제품 Recipe가 인증되지 않았다"는 말이 성립한다. 기계는 멀쩡한데 그 제품을 돌릴 조건이 등록되지 않은 상태다.  

**Dispatch**는 배차라는 말에서 온 듯한데, 여기서는 "다음에 어떤 LOT을 어느 설비에 넣을지 고르는 행위"다.  
나중에 알았지만 이게 이 글 전체에서 최적화가 들어갈 자리다.  

이 중 Lot → Route → Operation → Equipment 관계를 이해하면 데이터 모델이 보이기 시작한다.  

### LOT 하나가 어떻게 움직이나

![LOT A001이 CUTTING을 마치고 PROCESSING에서 87분째 대기 중인 상황. MES를 조회하면 EQ-04 대기열 8건, EQ-05 고장, EQ-06 Recipe 미인증이 나온다](/assets/images/2026-08-14-mes-basics/02-lot-flow.png)

LOT은 Route를 따라 이동하고, 각 공정마다 그 공정이 가능한 설비 중 하나에 배정된다.  
MES DB에는 이 과정이 계속 기록된다. 어느 시점의 상태는 이런 식이다.  

```
LOT: A001
Product: P100
Current Operation: PROCESSING
Equipment: EQ-04
State: WAIT
Wait Time: 87 min
Priority: HIGH
```

여기서 현장 엔지니어가 묻는다. A001은 왜 87분째 대기 중이지?  

MES를 조회하면 답이 나온다. EQ-04 대기열에 8개가 밀려 있고, EQ-05는 고장이고, EQ-06은 이 제품 Recipe가 인증되지 않았다.  
즉 EQ-05 장애로 가용 설비가 줄어서 줄이 밀린 것이다.  

이 조회 사슬이 그대로 에이전트가 붙는 자리이기도 하다.

## 상태가 핵심이다

### 상태 전이와 규칙

일반적인 서비스 DB와 다른 점이 여기다.  
MES는 수많은 객체의 현재 상태와 상태 전이가 핵심이다. CRUD가 아니다.  

LOT은 `WAIT → RUN → COMPLETE`가 기본이고 중간에 `HOLD`, `REWORK`, `SCRAP`이 끼어든다.  
설비도 `IDLE / RUN / DOWN / MAINTENANCE`로 계속 바뀐다.  

그리고 전이에는 규칙이 있다.  

* HOLD 상태의 LOT은 Dispatch할 수 없다  
* DOWN 상태의 설비에는 LOT을 투입할 수 없다  
* Recipe 인증이 없는 설비에는 해당 제품을 보낼 수 없다  

### 상태를 한 축에 몰아넣으면 안 된다

여기서 직접 만든 기획서의 결함을 하나 발견했다.  

처음에는 LOT 상태를 한 줄로 뒀다. `WAIT → DISPATCHED → PROCESSING → HOLD` 식이다.  
그런데 이러면 **HOLD를 해제할 때 어디로 돌아가야 하는지가 사라진다.**  
중단되던 작업을 이어서 하는 건지, 처음부터 다시 하는 건지, 다른 설비로 가는 건지 상태만 봐서는 알 수 없다.  

![왼쪽은 상태를 한 축에 둔 경우로 HOLD 해제 시 복귀 지점이 사라진다. 오른쪽은 Flow와 Control 두 축으로 나눠 PROCESSING에 머문 채 HOLD가 걸린다](/assets/images/2026-08-14-mes-basics/03-two-axis-state.png)

해법은 축을 둘로 나누는 것이었다.  

| Flow State (생산 진행) | Control State (통제) |
|---|---|
| `WAIT` 현재 공정 대기 | `NORMAL` 정상 |
| `DISPATCHED` 설비 배정됨 | `HOLD` 진행 차단 |
| `PROCESSING` 처리 중 | `QUARANTINE` 출하 보류 |
| `COMPLETED` 전 공정 완료 | |
| `SCRAPPED` 폐기 | |

두 축은 서로의 위치를 덮어쓰지 않고 독립적으로 움직인다.  
PROCESSING에 머문 채 HOLD가 걸리고, 해제하면 그 자리에서 이어간다.  

다만 모든 조합이 합법인 건 아니다.  
`COMPLETED + QUARANTINE`은 유효하다. 이미 만든 제품을 뒤늦게 격리하는 경우다.  
반면 `COMPLETED + HOLD`는 불법이다. 이미 끝난 걸 진행 차단할 수는 없다.  

한 축으로는 이 구분 자체를 표현할 수 없었다.

## 이름이 비슷한 시스템 구분하기

MES 주변에는 헷갈리는 시스템이 많다.  

| 시스템 | 역할 |
|---|---|
| ERP | 기업 전체 자원, 주문, 구매, 회계 |
| APS | 생산계획과 스케줄 최적화 |
| MES | 실제 생산 실행 및 추적 |
| SCADA | 설비 상태 감시 및 제어 |
| PLC | 기계 자체의 실시간 제어 |
| QMS | 품질 관리 |
| WMS | 창고 및 재고 이동 |

이 중 APS(Advanced Planning and Scheduling)가 제일 낯설었다.  
찾아보니 생산계획을 세우고 순서를 최적화하는 시스템으로, **내가 붙이려던 OR이 원래 살던 동네**가 여기였다.  
그러니까 나는 APS의 기법을 MES 쪽으로 끌어오려는 셈이다.  

질문으로 나누면 선명하다.  

* "내일 어떤 제품을 어느 순서로 생산할까" → APS  
* "현재 A001이 어디 있고 왜 멈춰 있나" → MES  
* "EQ-01의 모터를 멈춰라" → PLC  

실제 제품에서는 경계가 많이 겹치지만, 개념을 잡을 때는 이렇게 나눠두는 게 도움이 됐다.

## 근무표 문제와 닮았다

공부하다 보니 계속 기시감이 들었다.  

내가 하던 인력 근무표 문제는 사람과 근무 유형, 기간, 제약조건, 상태로 이루어져 있었다.  
MES는 LOT, 공정, 설비, 제약조건, 상태로 이루어져 있다.  

**둘 다 Entity + State + Constraint + Action 구조다.**  

제약의 성격도 비슷하다.  
"야간 근무 다음날은 주간 근무 금지"와 "Recipe 인증이 없는 설비에는 투입 금지"는 형태가 같다.  
자원에 작업을 배정하는데 시간 순서와 자격 조건이 걸린다는 점에서 다르지 않다.  

Dispatch를 "어떤 LOT을 어떤 설비에 언제 넣을 것인가"로 놓으면 그대로 스케줄링 최적화 문제가 된다.  
내가 근무표에서 쓰던 것을 여기에 가져올 수 있겠다고 판단한 근거가 이거다.

## 정리

* MES는 ERP의 생산계획을 현장에서 실행하면서, 생산지시와 LOT과 공정, 설비, 품질 상태를 실시간으로 연결하고 이력을 추적하는 시스템이다  
* ERP와 MES의 경계는 "무엇을 만들 것인가"와 "지금 어떻게 만들어지고 있는가"로 갈린다. LOT 분할은 MES의 권한이다  
* MES 구현의 핵심은 CRUD가 아니라 **상태 전이의 합법성**이다  
* 진행 상태와 통제 상태는 다른 축이다. 한 축에 몰면 HOLD 해제 시 복귀 지점을 잃는다  
* 근무표와 MES는 둘 다 Entity + State + Constraint + Action이다. 그래서 OR을 옮길 수 있다  

아직 못 본 것도 많다.  
개념은 잡았지만 실제 DB 스키마로 내려가면 또 다를 것이다. 특히 LOT 수량이 `양품 / 폐기 / 재작업`으로 갈라질 때 추적을 어떻게 유지할지는 아직 정리하지 못했다.  
그리고 이 글은 전부 개념이고 측정이 하나도 없다. 다음은 Route와 Dispatch를 실제 스키마로 설계하고, 설비 한 대가 멈췄을 때 WIP가 어떻게 밀리는지 시뮬레이션으로 재보려 한다.  
거기까지 가야 CP-SAT를 붙일 자리가 생긴다.
